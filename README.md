# IME - 통합 모니터링 환경

여러 게임의 공개 커뮤니티 글을 실시간으로 모아 한 화면에 보여 주고(**피드**), LLM 두 단계로 걸러 요약하는(**AI 요약**) 개인 프로젝트입니다. 게임 운영 모니터링을 하며 커뮤니티 확인이 다른 업무와 겹치면 병목이 생겨, 개발 요청 없이 혼자 기획하고 만들었습니다.

이 레포는 운영 코드에서 피드 · AI 요약 흐름만 떼어 낸 읽기용 스냅샷입니다. 범위와 빠진 부분은 아래 "비공개 범위", 스냅샷 기준과 이용 조건은 맨 아래 "이 레포에 대해"에 적었습니다.

## 어떻게 동작하나요

1. **수집** (`web_app/crawlers/crawler.py`, `content_extractor.py`) - 게시판마다 구조와 갱신 주기가 달라, 한 형태로 정리하고 중복을 지우는 것에서 출발했습니다.
2. **1차 판정** (`web_app/ai_lib/gemma4_summary_core.py`) - LLM이 글마다 "요약할 가치가 있나"만 예/아니오로 답합니다. 들어오는 글 대부분은 요약이 필요 없어서 이 단계를 앞에 두었습니다.
3. **2차 요약** (같은 파일, 사이클은 `web_app/web_lib/ai_gemma4_worker.py`) - 1차를 통과한 글만 다른 LLM이 요약합니다.
4. **화면** (`web_app/templates/partials/tabs/feed.html` · `ai_summary.html`) - 피드 탭과 AI 요약 탭으로 보여 줍니다.

수집 범위는 로그인 없이 보이는 게시판이 기본이고, 예외는 두 곳입니다. 한 게임 공식 카페의 게시판 한 곳은 목록은 누구나 볼 수 있지만 본문은 카페 회원에게만 보여, 카페 회원인 제 계정의 로그인 상태로 읽습니다. 자동 로그인은 하지 않고 비밀번호는 받지도 저장하지도 않습니다(`web_app/crawlers/content_extractor.py`). 댓글 수집기는 로그인한 브라우저 세션을 쓰고, 설정으로 켜고 끕니다(`web_app/web_lib/bg/contents.py`).

스택은 Python 3.11 · Flask · Flask-SocketIO · APScheduler · SQLite(WAL)입니다(2026-09-07 기준). 운영 서버는 저사양 홈 서버(2코어, AVX 없음)입니다.

## AI를 어디까지 썼나요

코드 대부분은 AI 코딩 에이전트(Claude Code 등)가 작성했고, 아래의 측정과 장애 원인 분석도 대부분 AI와 함께 했습니다. 제 역할은 무엇을 만들지 정하고(운영 모니터링 중 놓치던 글을 줄이는 것), 문제가 생기면 무엇을 확인할지와 어떤 해결책을 택할지 결정하고, 결과를 화면과 라이브 측정으로 검수하는 일이었습니다.

구조와 모델은 측정을 보고 바꿨고(표본 대조 · 처리 시간 비교, [`docs/pipeline-history.md`](docs/pipeline-history.md)), 운영 중 장애는 AI와 함께 원인을 좁혀 고쳤습니다([`docs/incidents.md`](docs/incidents.md)). AI가 쓴 코드는 시험(아래 "돌려 볼 수 있는 것"의 표)과 라이브 측정으로 검증했고, 검증이 틀렸던 사례도 기록에 남겼습니다.

## 먼저 볼 파일 세 개

1. `web_app/ai_lib/gemma4_summary_core.py` - 1차 판정과 2차 요약의 본체입니다. 호출 한도 · 재시도 · 폴백이 어디서 갈리는지 볼 수 있습니다.
2. `web_app/web_lib/ai_gemma4_worker.py` - 요약 사이클입니다. 아래 측정 1로 고른 배치 병렬화(v6.7.454)와, 2차 요약을 받지 못하고 밀린 글을 로그로 드러내는 부분(v6.7.436)이 있습니다.
3. `web_app/crawlers/crawler.py` - 수집 공통 엔진입니다. 공식 게시판 수집이 실패해도 빈 목록이 돌아와 "오늘 글 0건"과 구별되지 않던 것을 연속 실패 경보로 드러냈습니다(v6.7.739). 키 파일이 없을 때 멈추지 않고 돌아오는 가드(v6.7.747)는 `test_empty_sa_pool.py`가 지킵니다. 가드를 지우면 그 시험이 실패합니다.

## 측정으로 정한 것

### 1. 해결책 후보를 배포 전에 계산으로 거르기 (2026-07-28)

- **증상**: 요약 대기열의 꼬리 지연이 최대 10.82분이었습니다. 주기를 60초에서 20초로 줄이는 처방은 꼬리에 효과가 없었습니다.
- **먼저 측정**: 로그 3줄만 배포하고, 14시간 뒤 배치 한 번에 걸리는 시간을 식으로 세웠습니다. T(n) = 10.70 + 3.58n (n = 배치 수, R² 0.867, 28표본), 가동률(사이클 시간 중 실제로 일하는 비율) rho 0.98.
- **거르기**: 후보 4개(배치 크기 · 사이클 상한 · 주기 · 배치 병렬화) 가운데 사이클 상한 상향과 주기 단축은 계산상 이득이 0이라 배포 전에 뺐습니다. 배치 병렬화를 골라 사이클 140초 -> 91.2초, 처리량 분당 12.9 -> 19.7건, rho 0.64가 됐습니다.
- **예측과 달랐던 점**: 미리 예상한 rho 0.49는 맞지 않았습니다. 병렬 가속은 배치 수 / ceil(배치 수 / 워커 수)로 계산해야 했습니다.

### 2. 1차 입력 줄이기 - 바꾸기 전에 놓치는 글부터 쟀습니다 (2026-09-24)

- **증상**: 1차 입력의 약 90%가 2차용 공통 지침(13,807자)이었고, 이것이 분당 입력 토큰 한도를 차지해 한도 초과(429)가 계속 났습니다.
- **바꾸기 전**: 공통 지침에서 수집 · 제외 기준만 남긴 607자 전용 지침을 만들고, 층화 표본 두 개(140건)로 두 지침을 비교했습니다. 운영에서 요약 대상이던 글 가운데, 공통 지침은 잡는데 새 지침만 놓친 글은 0건이었습니다(운영에서 탈락이던 글 2건은 공통 지침만 통과시켰습니다).
- **결과**: 호출당 프롬프트 약 15,200자 -> 약 2,000자 (v6.7.687).
- **예측과 달랐던 점**: 1차 호출 시간은 줄지 않았습니다. 지연은 입력이 아니라 thinking이 만들고 있었고, 그 부분은 따로 풀었습니다(위 "모델 변천"의 2026-09-28 행).

## 장애 하나 - 유휴 뒤 첫 접속에서 11~16분 무응답 (2026-08-24 ~ 09-03)

- **증상**: 몇 시간 쉬고 난 뒤 첫 접속에서 사이트가 11~16분 응답하지 않았고, 자동 재시작이 일어나면 나았습니다. 자동 재시작 9건 중 8건이 같은 모양이었습니다.
- **헷갈린 점 둘**: "재시작하면 낫는다"는 원인을 고친 것이 아니라, 부팅이 DB 파일을 읽으며 캐시를 데워 놓았기 때문이었습니다. 앱 메모리(RSS)가 2배로 뛴 것은 누수처럼 보였지만 파일 매핑이었습니다.
- **좁힌 방법**: 같은 시각의 서버 지표 5종을 나란히 놓았습니다. 디스크 사용률 100%, CPU의 디스크 대기(iowait) 66~87%인데 CPU 연산은 평평했습니다. 연산도 메모리도 아니고 디스크 대기였습니다. 같은 요청을 두 번 재서(첫 호출 60초, 둘째 0.7초) "쿼리가 느리다"가 아니라 "캐시가 식었다"로 갈랐습니다. 방아쇠는 무응답 4초 전의 WebSocket 연결, 즉 사람이 페이지를 연 순간이었습니다.
- **원인 세 가지**:
  1. `WHERE DATE(timestamp) >= ?`처럼 컬럼에 함수를 씌운 조건이 인덱스를 쓰지 못해 전체를 훑었습니다(범위 밖 통계 화면의 질의라 이 스냅샷에서는 빈 자리표시입니다 - [장애 기록](docs/incidents.md)).
  2. 오래된 행을 지우는 보관 정책이 주석에만 있고 호출하는 곳이 없어 한 번도 돈 적이 없었습니다. 그래서 파일이 계속 커졌습니다.
  3. 헬스체크가 요청 스레드 풀 하나(1워커 × 8스레드, 2026-09-07 구성)에만 기대고 있었습니다. 스레드가 전부 디스크를 기다리면 DB를 쓰지 않는 생존 확인(`web_app/web_lib/routes/health.py`)도 차례를 받지 못해, "밀림"이 "죽음"으로 읽히고 재시작이 일어났습니다.
- **수정**: 조건을 접두 비교로 바꿔 인덱스를 쓰게 했고, 헬스체크에 요청 풀 밖의 근거(하트비트)를 하나 더했습니다. 보관 정책은 실제로 도는 작업으로 만들었지만 삭제 스위치는 일부러 꺼 두었습니다. 쌓인 데이터를 지울지는 운영에서 판단할 일이기 때문입니다.
- **결과**: 문제 경로의 첫 호출 60초 이상 -> 1.19초(2026-09-03 기준). 방아쇠를 확정하고 배포까지 하루가 걸렸습니다.
- **남은 미검증**: 완전히 식은 상태의 첫 접속은 이 기록 시점까지 관측하지 못했습니다.

## 비공개 범위 - 무엇을 넣지 않았나요

이 스냅샷의 범위는 **피드 · AI 요약 흐름**입니다. 운영 앱은 한 덩어리(모놀리스)라, 범위 밖 모듈을 그냥 빼면 넣은 코드의 import가 깨집니다. 그래서 범위 밖이지만 넣은 코드가 부르는 파일은 **같은 경로에 빈 자리표시 파일(스텁)**로 남겼습니다.

- **Python 스텁**: 넣은 코드가 가져가는 이름만 정의합니다. 함수 · 클래스는 호출하면 `NotImplementedError`를 내고, 값은 같은 종류의 빈 값(빈 문자열 · 빈 목록 등)입니다.
- **템플릿 · JS · CSS 스텁**: 주석 한 줄입니다. 화면에서는 그 탭이 비어 있습니다.
- 스텁으로 남긴 것: 범위 밖 화면 탭과 그 API(관리자 · 검색 · 통계 등), 부속 수집기, 일부 백그라운드 작업(알림 발송 · 백업 · 방문 기록 등), 공식 게시판 한 곳의 수집기, 운영 설정 값 한 자리(`web_app/utils/private_config.py` - 시트 주소 · 시트 공유 메일 · 공개 주소).
- 아예 넣지 않은 것: 1차를 로컬 분류기로 바꾸려 한 실험(학습 · 평가 · 서빙 코드, 학습 데이터, 모델 가중치 - 위 "모델 변천" 마지막 행), 수집한 원문 DB, 운영 배포 설정. `gemma4_summary_core.py` 안의 로컬 1차 분기(환경 변수로 켜고, 기본값은 Gemma)는 원본 그대로라 남아 있지만, 그 분기가 부르는 분류기 서비스는 이 레포에 없습니다.

파일별 출처(원본 그대로 / 스텁 / 빌드가 다시 만든 스냅샷)는 `SOURCE.tsv`에 있습니다. 다시 만든 계약 스냅샷 2개의 이유는 아래 시험 표 바로 위에 적었습니다.

## 돌려 볼 수 있는 것

앱을 띄우는 레포가 아니라 **읽기와 시험용 레포**입니다. 시험은 저장소 루트가 아니라 각 폴더 안에서 돌립니다. 웹앱 시험은 백그라운드 작업이 실제로 뜨지 않도록 `IMT_DISABLE_BOOTSTRAP=1`을 줍니다.

줄마다 저장소 루트에서 시작합니다:

```bash
cd web_app && IMT_DISABLE_BOOTSTRAP=1 python test_globals_state_contract.py
```

```bash
cd web_app && node tests/test_escape_html_v731.js
```

빌드가 스텁 상태로 다시 만든 계약 스냅샷입니다(원본 스냅샷은 범위 밖 코드의 결과를 담고 있습니다):

- `web_app/tests/pages_index_contract_snapshot.json` - index() 가 렌더하는 HTML 에 범위 밖 탭 템플릿이 들어 있다 - 스텁으로 바꾼 뒤 다시 찍었다
- `web_app/tests/bootstrap_jobs_snapshot.json` - 범위 밖 동향 리포트 잡의 발송 시각 목록이 스텁(빈 값)이라 등록 잡이 2개 준다 - 스텁 상태로 다시 찍었다
