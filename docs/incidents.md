# 장애 기록 - 세 건은 깊게, 한 건은 짧게

> 운영하며 겪은 장애 중 판단 과정이 남은 것만 골랐다. 순서는 증상 -> 함정 -> 근본 원인 -> 처방 -> 확인이다.
> 숫자마다 기준일을 붙였고, 재지 않은 것은 "기록 없음" 으로 적었다. 틀렸다가 고친 것도 지우지 않았다. 운영 서버는 저사양 홈 서버(2코어, AVX 없음)다.

## 1. 요약 대기열의 꼬리 지연 - 먼저 재고, 처방은 산수로 골랐다 (2026-07-28, v6.7.447 ~ v6.7.454)

- **증상**: 글이 들어와 요약이 뜨기까지 "5분? 10분?" 걸린다는 체감. 로그의 지연은 평균 1.79분, 중앙 1.20분, 최대 10.82분이었다(2026-07-28).
- **함정**: 평균과 중앙만 봤으면 정상으로 닫았을 것이다. 체감은 꼬리였다. 먼저 워커 주기를 60초에서 20초로 줄였는데(v6.7.447) 꼬리는 그대로였다 - 픽업 대기가 병목이 아니었다. 남은 후보(배치 크기 · 사이클 캡 · 주기) 중 무엇이 이득인지 계산할 근거가 없었다.
- **계측 먼저**: 처방을 보류하고 로그 3줄(배치 크기별 1차 콜 시간, 사이클 총 시간과 배치 수, 60초를 넘긴 사이클)만 배포했다(v6.7.453). 14시간 뒤 비용 모델이 나왔다. 1차 콜 T(n) = 10.70초 + 3.58초 × n (28표본, n=1~10, R² 0.867). 배치 10 기준 고정비는 23% 이고 77% 가 건당 비용이라, 배치를 아무리 키워도 순차 상한은 60 / 3.58 = 16.8건/분이다.
- **근본 원인**: 느린 파이프라인이 아니라 가동률 포화였다. 피크(19시 KST) 유입 12.6건/분, 순차 처리 상한 12.9건/분 - 가동률 rho 0.98. rho 가 1 에 가까우면 대기 지연은 비선형으로 커진다. 평시 저녁에는 요약 대기가 4건(평균 1.2분)뿐이었다. 하루 2~3시간만 포화한 것이다.
- **처방**: 후보를 "절편을 건드리나, 기울기를 건드리나" 로 나누자 절반이 배포 전에 빠졌다.

| 후보 | 처리량 | rho | 판정 |
|---|---:|---:|---|
| 현행 | 12.9건/분 | 0.98 | 포화 |
| 배치 크기 10 -> 20 | 14.6건/분 | 0.86 | 절편만 줄어 부족 |
| 사이클 캡 상향 | 12.9건/분 | 0.98 | 순이득 0 - 순차라 배치 수만 는다 |
| 주기 단축 | 12.9건/분 | 0.98 | 순이득 0 - 이미 틱의 81% 가 건너뛰어진다 |
| **배치 병렬화 (채택)** | **19.7건/분** | **0.64** | 기울기를 건드린다 |

- 병렬화의 전제로 공유 상태 세 가지를 같이 고쳤다. 이것이 작업의 대부분이었다. 배치끼리 같이 쓰던 API 클라이언트를 배치마다 따로 쓰게 했다(한 배치의 키 교체가 다른 배치의 진행 중 호출을 흔들었다). 전역 5초 간격 제한을 키별로 나눴다(그대로면 둘째 배치가 5초를 자서 병렬화를 되돌린다). 호출 한도를 세는 2차 요약은 메서드 안의 락으로 직렬화했다(호출처가 둘이라 호출처마다 걸면 하나를 빠뜨린다).
- **확인**: 배포 직후 라이브 로그에서 1차 배치 두 개가 2.7초 차로 끝났다(45.1초 · 47.7초) - 실제로 동시에 돌았다. 사이클 140초 -> 91.2초(-35%), 처리량 12.9 -> 19.7건/분(+53%), rho 0.98 -> 0.64 (2026-07-28). 배치별 콜 시간이 모델값 T(10) = 46.5초와 같아, 병렬 호출이 서로를 늦추지 않는다는 전제도 확인됐다.
- **자기 정정**: 배포 전에 예고한 rho 0.49 는 틀렸다. 2배 가속을 가정했지만, 사이클당 배치 3개를 워커 2개가 돌면 2+1 의 두 차례라 1.5배다. 두 차례 모델의 예측 93.5초와 실측 91.2초가 맞았으니, 틀린 것은 비용 모델이 아니라 병렬도와 배치 수를 맞춰 보지 않은 것이다. 병렬 가속은 워커 수가 아니라 배치 수 / ceil(배치 수 / 워커 수) 다.
- **코드**: `web_app/web_lib/ai_gemma4_worker.py`(배치 병렬 실행), `web_app/ai_lib/gemma4_summary_core.py`(배치별 클라이언트, 키별 간격, 2차 락). 병렬도는 2026-09-09 에 2에서 4로 올려(v6.7.652) 스냅샷 코드에는 4가 들어 있다. "처리량 결함은 평균 지연이 아니라 가동률로 진단하고, 처방은 절편과 기울기로 나눈다" 를 재발 방지 규칙으로 남겼다.

## 2. 유휴 뒤 첫 접속에서 11~16분 무응답 (2026-08-24 ~ 09-03, v6.7.627)

- **증상**: 몇 시간 쉰 뒤 첫 접속에서 사이트가 11~16분 응답하지 않았고, 헬스체크 실패로 자동 재시작이 일어나면 나았다. 2026-08-24 ~ 09-03 의 자동 재시작 9건 중 8건이 같은 모양이었고, 배포가 없는 날에도 났다.
- **함정**:
  - "재시작하면 낫는다" 가 진단을 거꾸로 끌었다. 재시작이 고친 것이 아니라 부팅이 DB 파일을 읽어 캐시를 데워 놓아, 재시작 직후에는 재현되지 않았을 뿐이다.
  - 앱 메모리(RSS)가 2배로 뛰어 누수처럼 보였다. 실제로는 커넥션의 mmap 이 읽은 파일 페이지였고, 익명 메모리는 오르지 않았다.
  - 단독으로 재도 첫 호출은 60초가 나와 "쿼리가 느리다" 로 읽힌다. 두 번째 호출이 0.7초여서야 "캐시가 식었다" 로 갈렸다. 두 번 재야 한다.
- **좁힌 방법**: 30초 간격 호스트 지표 5종을 사고 시각에 맞춰 나란히 놓았다. 무응답 동안 디스크 busy 100% 연속(평시 8~19%), 코어당 iowait 66~87%(평시 2~9%), CPU user 8~17%(평시 6~12%, 평평), 앱 요청 카운터는 0 이 6분 연속이었다. 읽기 1건이 5~8KB 라 SQLite 페이지 단위 랜덤 읽기였고, 100~150 IOPS 는 단일 HDD 의 천장이다. 연산도 메모리도 아닌 디스크 대기다. 방아쇠는 무응답 4초 전의 WebSocket 연결, 즉 사람이 페이지를 연 순간이었다. 접속 직후 요청이 분당 50~577건 쏟아졌다.
- **근본 원인 (3단)**:
  1. 통계 조회가 `WHERE DATE(timestamp) >= ?` 처럼 컬럼에 함수를 씌워 인덱스를 못 타고 테이블 전체를 훑었다. SQLite 는 이때 경고하지 않는다.
  2. "7일 보관" 은 주석에만 있었다. 보관 삭제 함수의 호출부가 0 이라 4월부터 쌓여 파일이 15배 커져 있었다. 캐시에 다 들어갈 크기였으면 1 이 있어도 안 났다.
  3. 헬스체크가 요청 스레드 풀 하나(1워커 × 8스레드)에만 기댔다. 스레드가 전부 디스크를 기다리면 DB 를 안 쓰는 생존 확인도 차례를 못 받는다. 헬스체크 10회 실패(5분)면 재시작이라, "밀림" 이 "죽음" 으로 읽혔다.
- **처방**: 앞의 하나는 방아쇠 제거, 나머지는 증폭 차단이다.
  - 조건을 `timestamp >= 'YYYY-MM-DD'` 로 바꿨다. 값이 ISO 19자라 접두 비교가 곧 날짜 비교다. 전체 이력을 묶던 통계는 7일 창 + `INDEXED BY` + 60초 캐시로 바꿨다.
  - 헬스체크에 요청 풀 밖의 근거를 하나 더했다. 워커 안 스레드가 10초마다 하트비트 파일을 갱신하고, HTTP 가 실패해도 하트비트가 90초 안이고 실패가 20분 미만이면 살아 있다고 본다.
  - 자동 재시작 장치의 정지 대기를 10초에서 60초로 늘렸다(앱 종료에 44초가 걸려 재시작이 두 번 찍혔다). 그 장치를 다음에 다시 만들 때 적용된다.
  - 보관 정책을 실제로 도는 잡으로 만들었지만(2,000행씩 나눠 삭제) 스위치는 꺼 뒀다. 쌓인 데이터를 지울지는 운영 판단이고, 성능은 앞의 둘로 잡는다.
- **확인**: 배포 4분 뒤 재기동 후 첫 호출로 쟀다(2026-09-03). 통과율 통계 60초 넘음(504) -> 1.19초(2회차 0.47초), 데이터 통계 16초 -> 0.39초(2회차 0.30초). 배포 22분 뒤 사람이 손대지 않은 자연 실험이 왔다. 새 방문자 접속으로 요청이 분당 240건(사고 때와 같은 급)이었는데, 요청 0 구간 없음, 디스크 busy 72% 한 샘플 뒤 26%, load 최고 1.9(사고 때 12.6), 재시작 없음.
- **미검증**: 자연 실험 때 캐시 상주율은 80%/51% 였다(재부팅 22분 뒤). 몇 시간 유휴로 완전히 식은 상태의 첫 접속은 아직 관측하지 못했다. 2026-09-08 에 다시 봤을 때도 미관측이다 - 그날 디스크를 포화시킨 것은 유휴가 아니라 같은 디스크를 쓰는 다른 앱이었다. 확인 방법(접속 전 상주율, 접속 후 요청 0 구간 부재)은 남겨 뒀다.
- **코드**: 바꾼 통계 API · 하트비트 · 보관 잡은 이 스냅샷 범위 밖이라 스텁이다. 잡 등록 자리는 `web_app/app.py`, 호출부가 0 이던 옛 보관 삭제 함수(`purge_old_data` - 새 잡은 이 함수를 부르지 않고 2,000행씩 나눠 지운다)는 `web_app/utils/sqlite_handler.py`, 요청 풀 안의 생존 확인은 `web_app/web_lib/routes/health.py` 에 있다. "컬럼에 함수를 씌우지 않는다 / 헬스체크는 요청 풀 밖의 근거를 하나 더 갖는다 / 보관 정책은 호출부가 있어야 정책이다" 를 재발 방지 규칙으로 남겼다.

## 3. 기각된 모델을 다시 재 보니 설정 탓이었고, 진짜 정지는 끝나지 않는 호출 하나였다 (2026-09-27 ~ 28, v6.7.697 ~ v6.7.699)

- **증상**: 요약이 피크마다 밀렸다. 라이브 로그를 쪼개니 사이클 시간이 곧 1차 판정 시간이었다. 1차 콜 하나가 1~4건에 42~83초였다(2026-09-28). 같은 창에서 1차 모델의 500 으로 배치가 통째로 실패한 사이클이 약 4분의 1(13사이클 중 3회)이었다.
- **함정**: 레포에 "불가능" 으로 적힌 것이 둘 있었다. "이 모델은 thinking 을 끌 수 없다"(`thinking_budget=0` 이 400 으로 거절된 실측), "더 작은 26B 는 이 판정에 못 쓴다(0/8)"(thinking 이 출력 상한을 다 태우고 답 0자). 둘 다 실측이었다. 틀린 것은 값이 아니라 잰 조건의 범위였다.
- **재현부터**: 결과를 보기 전에 판정 기준을 적고, 같은 10건으로 26B 를 다시 쟀다(2026-09-27).

| 조건 (26B) | 결과 |
|---|---|
| 기존 설정(온도 0 + thinking 켬) | 재현 - 답 0자, 한 콜 348초(3주 전 기록 346초). 같은 창의 31B 는 정상이라 서버 탓이 아니다 |
| 새로 받은 키 | 똑같이 재현 - 키 · 한도 탓이 아니다 |
| `thinking_budget=0` | 400 거절(기록 그대로) |
| **`thinking_level="minimal"`** | **정상 종료, 10건 중 9건 정답, 5초** |
| thinking 켬 + 온도 1.0(벤더 권장값) | 정상 종료 - 폭주 조건은 온도 0 과 thinking 의 조합 |

- "못 끈다" 는 끄는 방법 하나만 시도한 결론이었다. 끄면 무엇을 잃는지는 과제별로 쟀다. 1차 판정은 꺼도 라벨이 하나도 안 바뀌었고 시간만 31B 78 -> 28초, 26B 43 -> 4초(10건). 1차 재현율은 26B 7/10 = 31B 7/10(20건). 요약은 떨어졌다 - 31B 50 -> 42점, 26B 49 -> 46점(10건, 모델 이름을 가린 채점). 그래서 1차만 끄고 요약은 그대로 뒀다.
- **근본 원인 (두 번째)**: 1차가 빨라지자 숨은 정지가 드러났다(2026-09-28 저녁). 1차는 2.2초에 끝났는데 2차에서 Gemini 3.7 Flash 요청 하나가 18분 35초 응답 없이 붙잡힌 뒤 503 이었다. 사이클 하나가 1,487초였고, 사이클이 직렬이라 그동안 1차도 못 돌아 약 25분 멈췄다. 호출 시간 상한이 없던 이유도 레포의 "이 SDK 버전은 timeout 이 적용되지 않는다" 는 서술이었다. 10초 미만을 주자 서버가 `Minimum allowed deadline is 10s` 로 거절했다. 상한이 서버까지 실린다는 뜻이다.
- **처방**: 1차는 `thinking_level="minimal"`, 주력을 26B 로 하고 31B 는 폴백으로 돌렸다(재현율이 같고 10배 빠르다). 폴백도 반드시 thinking 을 끄고(폭주 조합 차단), 폴백까지 실패하면 첫 모델의 원래 오류를 올린다. 2차는 Flash 에만 호출 상한 30초 + 재시도 없음, 20초 넘게 걸려 실패한 Flash 는 30분 쉰다. 정상도 100초가 넘는 비상용 요약 모델에는 상한을 걸지 않았다.
- **확인**: 1차 콜 42~83초 -> 2~4초, 500 으로 배치가 통째 실패하던 약 4분의 1 -> 0(폴백이 2~4초에 받는다), Flash 과부하 때 2차 체인 25분 -> 약 2분(2026-09-28). 1차는 배포 직후 로그 끝의 판정 모델명과 시간으로, 2차 상한은 같은 과부하가 다시 온 창에서 "타임아웃 30초 ... 1800초 쿨다운" 로그가 실제로 찍히는 것으로 봤다. 장애 조건에서 고친 경로가 도는 것을 확인했다.
- **자기 정정**: 1차 목표를 "31B + thinking 끔으로 20초 미만" 으로 미리 적었는데 라이브는 20~70초로 미달이었다. 나머지는 31B 엔드포인트 자체의 지연이었다. 그래서 26B 를 주력으로 올리기 전에 재현율을 한 번 더 쟀다. 또 처음에는 0/8 기각 기록을 확인하지 않고 26B 를 후보로 올렸다. 기록을 무시해도, 믿기만 해도 틀렸을 것이다.
- **미검증**: 재현율 비교는 20건이라 "26B 가 못하다는 근거가 없다" 까지만 말할 수 있다. 요약 채점은 채점자 1명 · 1회 · 한 주제 10건이다. 배포 직후 약 10분의 DB 쓰기 락이 배포 3회 모두에서 재현됐다(유실 없음). 원인은 조사하지 않았다.
- **코드**: `web_app/ai_lib/gemma4_summary_core.py`(1차 설정 · 폴백, 2차 상한 · 쿨다운), timeout 서술을 고친 주석은 `web_app/ai_lib/genai_client.py`, 시험은 `web_app/test_ai_resilience.py`. "폴백이 첫 실패의 원인을 덮지 않는다" 는 앞서 재발 방지 규칙으로 남겨 둔 것을 따랐다.

## 짧게 - 인덱스가 있는데 못 쓰던 목록 쿼리 (2026-07-26 ~ 27, v6.7.437 · v6.7.444)

AI 요약 탭만 늦게 떴다. `EXPLAIN QUERY PLAN` 은 `SCAN ... USING INDEX` 였다. "인덱스를 타니 괜찮다" 로 읽기 쉬운 자리지만, `ROW_NUMBER() OVER (PARTITION BY ...)` 가 최근 3일 행 전부를 훑느라 138~190ms 가 걸렸고 그중 97% 가 분석 제외 행이었다(2026-07-26). 같은 때 피드 목록은 인덱스 끝에서 필요한 만큼만 걸어 2.6ms 였다. 처방은 유효 행만 담는 부분 인덱스, 그리고 저장 직후 캐시를 비우는 대신 쓰기 쪽에서 미리 계산해 채우는 것이었다. 로컬 벤치(라이브 비율을 흉내 낸 DB)에서 713ms -> 44ms(2026-07-26)였고, 라이브 138ms -> 8.8ms 는 출처가 한 곳뿐이라 측정일과 재측정은 기록 없음. 남은 함정은 부분 인덱스가 쿼리 WHERE 가 인덱스 WHERE 를 포함할 때만 쓰이고, 어긋나면 에러 없이 조용히 안 쓰인다는 것이다. 그래서 술어를 상수 한 곳(`AI_NOTABLE_FILTER`)으로 묶었다. 같은 원인의 다른 목록(2026-10-24 에 화면째 지웠다)은 키 목록을 재귀 CTE 로 먼저 얻고 키마다 `LIMIT N` 을 도는 느슨한 인덱스 스캔으로 바꿔, 같은 읽기 스냅샷에서 행 집합과 순서가 같은 것을 확인하고 1.395초 -> 0.0019초였다(2026-07-27). 코드는 `web_app/utils/sqlite_handler.py`(`AI_NOTABLE_FILTER`, 부분 인덱스)와 `web_app/web_lib/routes/analysis.py`(미리 채우는 캐시, `_build_ai_summary_payload`). "부분 인덱스의 술어는 한 곳에 두고, 쓰이는지는 플랜에 인덱스 이름이 나오는지로 본다" 를 재발 방지 규칙으로 남겼다.
